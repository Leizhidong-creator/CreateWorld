# 剧情驱动的核心玩法

从剧情推导：玩家目标、阻碍、已知与未知信息、可操作对象、状态变化、反馈、失败与恢复。先明确操作为何会产生剧情结果，再选择实现。
通用框架只复用移动、输入、场景、状态等能力，不固定玩法。组件适合时复用；不适合时实现本作简单机制。机制可发生在探索场景或独立小游戏，不强制每场一个弹窗。
第一版控制规则数量和实现成本，保留关键因果。例如离散线路连接可以模拟修复，不必完整电路物理。不能用拾物后一句“完成”替代已要求的操作过程。不要人为等待或重复点击凑时长。
用简洁mechanics规格写剧情依据、目标、信息、输入、规则、反馈、成功/失败/取消、状态接口和实际操作测试。贯穿多个场景时说明如何复用与组合。无需固定三方案或每动作长报告。
可以自主制作最小实现验证不确定机制，再返回设计。验证失败修规则或实现，不能删掉机制冒充完成。核心机制必须映射到实现位置及可执行测试；纸面结果不等于运行通过。

在 Create World 工作台内使用时，先按需读取 [项目接入约定](references/workbench-v2.md)。技能可在完整任务中重复调用，不规定固定流水线。旧格式参考仅用于对应旧项目，不能覆盖当前合同。

## 小游戏库（100 种）

需要"一个可操作的小游戏或小谜题"而本作机制尚未确定时，先读 [小游戏库](references/minigame-library.zh-CN.md)。用法固定：

1. **先取索引**：工作台内调用 `cw_minigames`（无参数列出 10 类及各自回答的问题；传 `category` 列该类 10 条；传 `id` 取单条摘要与正文路径）。不在工作台内时，读 `references/minigame-index.json`。按"这段剧情要玩家回答什么问题"挑 1–3 个候选。
2. **只读候选条目**：用 ID 定位（如 `A03 痕迹追踪`），读它的玩法、判定、入戏、落地、界面、验收六段；不要通读全库。
3. **改造再落地**：把道具、语言、失败后果换成这部作品的；在 `mechanics` 里加 `"libraryRef":"A03"`，并在 `storyBasis` 写清它替剧情回答了什么。
4. **限两个**：同一部作品最多用 2 个库内机制，且不得同类重复（两个密码、两个拼图）；其余机制自行设计。
5. **不许照抄**：条目里的数值、界面尺寸是起点，不是答案；直接复制一套设置等于换皮，验收时按"机制是否映射到本作剧情"判断。

库内每条的**界面**与**验收**两段可直接作为实现自检与 `journeys` 测试的起点：界面给 640×360 下的布局与尺寸，验收给三条结局路径要断言的数值。
