# Create World 新工作流 V1（草案）

这是一版用于评审的工作流设计，不修改现有实现。目标是把“故事到可玩游戏”拆成更短、更可控的生产链，同时给速度、费用和画面质量留下明确的取舍入口。

## 一、总体判断

现有工作流把故事理解、玩法设计、内容写作、素材生产、编译、浏览器测试和审查交给一个长时间自主任务。它的优点是自动化程度高，缺点是：

- 一次任务太长，早期方向错误会在后面放大；
- 模型调用、浏览器回归和生图容易重复，费用不可预测；
- 文字、地图、碰撞和美术之间的返工边界不清楚；
- “能运行”与“画面精美”在同一条流水线竞争资源。

V1 改成“短阶段、确定性产物、按需升级”的生产方式：先快速证明故事和玩法，再决定哪些内容值得花钱做高质量美术。

## 二、核心生产链

```text
输入故事
  ↓
故事包（Story Pack）
  ↓
可玩切片（Playable Slice）
  ↓
低成本灰盒游戏（Graybox Build）
  ↓
内容锁定（Content Lock）
  ↓
定向美术升级（Art Upgrade）
  ↓
轻量验收（QA Gate）
  ↓
导出发布包
```

每一阶段都必须产出可检查文件；下一阶段只读取上一阶段已锁定的内容。这样可以避免“模型边写剧情、边改地图、边生成图片、边测试”的长循环。

## 三、四种工作模式

用户创建项目时先选择模式，之后也可以升级，但不能隐式增加预算。

| 模式 | 目标 | 默认素材 | 模型调用 | 适合场景 |
| --- | --- | --- | --- | --- |
| 极速 | 尽快得到可玩的故事原型 | 灰盒、复用角色和色板 | 1 次故事整理 + 1 次玩法整理 | 验证题材和流程 |
| 经济 | 控制成本并完成可发布原型 | 复用素材 + 少量新图 | 只为缺口调用 | 大量短篇项目 |
| 平衡 | 速度、费用、画面均衡 | 关键场景和主角定制 | 关键节点调用 | 默认推荐 |
| 视觉 | 优先画面完成度 | 定制角色、场景、动作和特效 | 多轮图像与人工审查 | 宣传样片、重点作品 |

模式只影响预算和素材策略，不降低基本可玩性和数据完整性要求。

## 四、阶段设计

### 阶段 0：输入清洗（本地、确定性）

输入：TXT、Markdown、字幕、用户粘贴文本。

处理：本地切段、去重、语言检测、章节识别、长度统计、敏感内容和空输入检查。这里不调用模型。

产物：

- `input/source.txt`：原文只读副本；
- `input/segments.json`：带行号和来源位置的片段；
- `input/brief.json`：标题、语言、长度、用户目标和模式。

失败时直接返回输入问题，不启动后续制作。

### 阶段 1：故事包生成（一次模型调用）

模型只做结构化提取，不写游戏代码、不生成图片。输出固定 JSON：

```json
{
  "premise": "...",
  "playerRole": "...",
  "beats": [{"id":"b1","sourceRefs":["seg-12"],"summary":"..."}],
  "characters": [{"id":"hero","role":"...","visualTags":[]}],
  "locations": [{"id":"home","purpose":"..."}],
  "mustKeep": [],
  "unknowns": [],
  "suggestedEnding": "..."
}
```

规则：每个关键事实必须带 `sourceRefs`；无法确认的内容进入 `unknowns`，不能用模型记忆补齐。用户可在这里修改故事包，修改后重新生成下游内容。

### 阶段 2：玩法切片（一次模型调用 + 本地校验）

只设计一条 3–8 分钟的主路线，不先制作整部游戏。模型输出：

- 玩家目标；
- 3–5 个关键行动；
- 每个行动的输入、成功、失败、取消和反馈；
- 2–4 个场景节点；
- 一个最能代表故事的互动机制。

本地校验检查：路线可达、所有节点有入口和出口、每个机制都有真实输入、失败和取消路径。校验不过就只重试这一阶段。

产物：`slice.json`、`slice-journey.json`。

### 阶段 3：灰盒首版（确定性模板）

编译器使用统一的灰盒素材：色块场景、通用角色、文字对白和程序化音效。此阶段不生图，不做复杂动画。

目标不是“看起来完成”，而是验证：

- 玩家是否知道下一步做什么；
- 移动、碰撞、交互、对白和小游戏是否成立；
- 关键故事节拍是否能在游戏中被实际经历；
- 失败、取消、刷新和存档是否可恢复。

灰盒必须在本地浏览器完成一条真实路线，时间目标为几十秒到数分钟。灰盒不通过，禁止进入美术生产。

### 阶段 4：内容锁定

用户或项目负责人确认以下内容后生成 `content-lock.json`：

- 场景数量和连接关系；
- 主角、主要 NPC 和关键物件；
- 对白、选项、任务和结局；
- 关键玩法规则；
- 不再接受会改变空间结构的普通文字修改。

内容锁定后，修改分为两类：

- 内容修改：对白、提示、颜色、数值，可快速重编译；
- 结构修改：新增场景、改路线、改碰撞、改机制，需要回到阶段 2 或 3。

### 阶段 5：定向美术升级

美术不再一次性覆盖整部游戏，而是按“玩家看到的价值”排序：

1. 标题图和首个场景；
2. 主角和主要 NPC；
3. 关键剧情场景；
4. 关键互动对象；
5. 过渡场景、装饰、动作和特效。

每个资源任务带有 `reuseKey`、`styleKey`、`sourceHash` 和 `qualityTier`。只有输入或风格发生变化时才重新生成。低价值资源继续使用灰盒或复用素材。

建议先固定一张“风格板”：像素尺寸、镜头、轮廓、调色板、光照方向、角色比例。先生产主角和一个场景做风格验证，通过后再批量生成同风格资源。

### 阶段 6：轻量验收

验收拆成三个小检查，不再每次都跑完整审查：

1. **结构检查**：JSON、资源引用、构建清单、存档版本；
2. **行为检查**：主路线、失败、取消、刷新、结局；
3. **视觉抽检**：首屏、主角、关键场景、关键互动对象。

只有发生以下变化时才扩大验收范围：

- 改了场景几何或碰撞；
- 改了运行时或扩展代码；
- 改了角色图集布局；
- 改了主线条件、结局或存档结构。

## 五、成本和速度控制

### 默认预算策略

- 故事理解：固定 1 次结构化调用；
- 玩法切片：固定 1 次结构化调用；
- 灰盒：本地确定性生成，不调用图像模型；
- 美术：只为变化的资源调用，按资源 ID 缓存；
- 修复：只重跑失败阶段，不重跑整部制作；
- 验收：改动影响哪个层，就只检查哪个层。

### 快速失败机制

- 每个阶段有明确超时和最大重试次数；
- 同一错误第二次出现时停止自动重试并展示诊断；
- 任务日志按阶段保存，允许从最近的稳定产物恢复；
- 不把“模型说完成了”当作通过条件。

### 三种资源预算

```text
时间预算：本地计算时间 + 模型等待时间
模型预算：文本调用次数 + 图像调用次数
返工预算：允许回退的阶段和资源数量
```

项目页面应该直接显示这三项，而不是只显示一个笼统的“制作中”。

## 六、和现有工作台的关系

V1 不需要立即重写运行时。可以先复用：

- `packages/runtime`：游戏运行能力；
- `packages/compiler`：构建和导出；
- `packages/browser-runner`：真实输入验证；
- `packages/assets`：资源缓存和质量记录。

### 固定源码库接入

V1 把移动、地图和情境交互作为基础能力，不让每个故事重新实现。工作台内置 `packages/source-library/world-kit/`，并通过 `world-kit` skill 暴露给后续 AI。需要这些能力时，AI 先读取该 skill，再复用 `index.js` 的固定入口：

- `mountWorldControls`：摇杆和交互键；
- `nearestInteraction`：最近交互目标排序；
- `drawWorldMap`：地图、任务区域提示、迷雾和玩家标记；
- `VIEWPORT`、`CONTROL_LAYOUT`、`MAP_LAYOUT`：固定坐标合同。
- `GAME_ASPECT_RATIO`、`assert16x9`：所有游戏画布保持 16:9，容器只等比缩放。

这样可以减少重复代码、减少触屏和地图回归测试，并把题材定制集中在主题、资源和回调。固定源码库的版本变更必须创建新版本目录，不能让单个项目静默改变全局坐标。

需要替换或缩小的是：

- `packages/orchestrator` 的长时自主循环；
- 一次性完成整部游戏的提示词；
- 默认先生产全部正式美术的策略；
- 每次修改都执行完整构建、完整浏览器回归和独立审查的策略。

第一版实现可以保留旧接口，新增一个 `workflowVersion: "v1-slice"`，让两套流程并行验证，确认速度、费用和画面质量后再删除旧流程。

## 七、V1 的成功标准

先不以“任意故事都能自动生成成品”为目标，而以可测量指标判断是否值得继续：

- 从输入到可玩灰盒的等待时间明显短于现有流程；
- 同一故事的模型调用次数和图像调用次数可预估；
- 修改对白不触发场景和素材重做；
- 修改场景结构能明确回退到正确阶段；
- 默认模式下首屏、主角和关键场景的视觉质量达到可接受水平；
- 失败时能保留最近一个可运行版本。

## 八、待评审问题

1. 默认模式是否采用“平衡”，还是默认“极速”？
2. 用户是否需要在阶段 2 亲自确认玩法切片？
3. 内容锁定是否由用户点击确认，还是项目负责人配置自动确认？
4. 视觉升级应按资源逐项收费/计量，还是按整套风格包计量？
5. 第一批验证故事应选一个短故事，还是直接拿《尘埃之外》做迁移对照？
