# 从完整 YAML 到场景切片的游戏生成工作流方案

> **实施状态（2026-10-30）**：核心链路已实现，落地合同、schema、闭包规则和验收语义见 [SCENE-SLICE.md](SCENE-SLICE.md)。本文保留为方案论证与问题清单；第 12 节“对当前项目实现的建议”中的 1–6 项已有对应实现，第 7 项（一致性检查）目前是保守哈希失效。

## 1. 背景

当前项目原本以故事文字、Markdown 或作品名作为输入，由工作台中的 Agent 自主完成来源整理、改编设计、玩法设计、状态设计、交互实现、素材生产、构建和真实运行验收。

为了让游戏内容更结构化，我们新增了一套内容规范和 YAML 内容档案：

- `content-spec/2D-pixel-story-content-spec.md`：描述 2D 像素剧情游戏内容应如何组织、引用、表达和验收。
- `content-spec/high-wall-beyond.game.yaml`：按该规范记录《高墙之外》的完整游戏内容。

用户后续的设想是：先把用户提示词整理成结构化 YAML，再根据 YAML 制作游戏。当前又进一步确定，第一版只制作一个场景，用于验证内容到游戏的转换质量。

## 2. 当前问题

完整 YAML 作为总档案是合理的，但不适合每次制作单个场景时完整注入 Agent 上下文。

对当前《高墙之外》YAML 的粗略统计如下：

- 文件大小约 274 KB
- 约 15 万字符
- 约 8497 行
- 粗略约 8 万至 12 万 token，具体取决于 tokenizer
- 包含 15 个场景和约 69 个事件

这份 YAML 还包含角色、物件、信息、状态、规则、声音、玩法、主线、检查点、结局、收集、行为记录、来源、设计记录和验收说明。

如果制作 `S_LIVING` 一个场景时仍然读取完整 YAML，可能造成：

1. 生成时间增加。
2. 上下文费用增加。
3. 与当前场景无关的信息分散 Agent 注意力。
4. 当前场景的条件、角色、物件和状态更容易被遗漏。
5. 修改一个场景时反复处理整部游戏材料。
6. 长上下文失败后，重试成本更高。

因此，问题不是“YAML 是否有必要”，而是“完整 YAML 是否应该在每个局部任务中完整作为生成输入”。

## 3. 核心判断

完整 YAML 应该保留，但应承担“权威内容数据库”的职责，而不是每次都作为完整提示词发送给 Agent。

更合适的职责划分是：

| 内容 | 职责 |
|---|---|
| 完整 YAML | 保存整部游戏的权威事实、关系、规则、来源和验收边界 |
| Markdown 规范 | 规定 YAML 的结构和游戏内容表达规则 |
| 场景索引 | 快速定位场景、事件、角色、物件、状态和依赖 |
| 场景切片 | 当前一次制作任务真正提供给 Agent 的局部输入 |
| 生成结果 | 回写到项目产物并接受结构、运行和内容检查 |

也就是说，YAML 转换过程仍然是必要的，但完整 YAML 更像数据库，场景切片才像本次任务的工作材料。

## 4. 建议的总体工作流

```text
用户提示词
    ↓
结构化整理为完整 YAML
    ↓
Markdown 规范校验
    ↓
ID、引用、条件、状态和场景连通性校验
    ↓
建立可查询的内容索引
    ↓
根据本次目标提取 scene-slice.yaml
    ↓
Agent 读取规范相关章节 + 当前场景切片
    ↓
设计并实现当前场景
    ↓
构建、真实输入测试、内容审查
    ↓
将结果和验证证据回写项目
    ↓
必要时重新提取受影响场景切片
```

## 5. 完整 YAML 的保留方式

完整 YAML 不应被删除或永久拆散。它应作为项目的唯一权威事实源，保留以下内容：

- 全部场景和事件
- 角色身份、动机、关系和知识边界
- 物件归属、合法用途、组合和消耗
- 状态定义、初值、变化来源和持久性
- 主线顺序、检查点和结局
- 来源记录和设计记录
- 用户决定、Agent 设计和验证边界

完整 YAML 的修改必须经过结构校验。不能只修改切片而不回写总档案，否则不同场景之间会逐渐产生冲突。

## 6. 场景切片应包含什么

对指定场景，例如 `S_LIVING`，场景切片不应只是复制场景对象本身，而应包含完成当前场景所需的最小闭包。

### 6.1 必须包含

- 当前场景记录
- 当前场景涉及的主线事件
- 当前场景的直接前置事件
- 当前场景的直接后续事件或出口条件
- 当前事件引用的角色
- 当前事件引用的物件
- 当前事件引用的信息
- 当前事件引用的玩法
- 当前事件读写的状态
- 当前场景相关的声音
- 当前场景涉及的规则
- 当前场景的来源和设计记录
- 当前场景的验收要求

### 6.2 可以只保留引用的内容

以下内容默认不完整展开，只保留 ID、名称和文件定位：

- 与当前场景无关的远期结局
- 其他场景的完整布局
- 其他场景的角色日常行为
- 不会在当前场景披露的秘密
- 与当前场景无关的收集内容
- 其他小游戏的完整规则

如果当前场景的条件依赖远期状态，只保留该状态的定义、当前值和依赖说明，不需要展开所有会改变它的远期事件。

### 6.3 场景切片的边界

切片必须声明：

- `sourceDocument`：完整 YAML 的路径或版本
- `sceneId`：当前制作场景 ID
- `includedIds`：实际展开的 ID
- `referencedIds`：只保留引用的外部 ID
- `scopeMode`：`scene-slice`
- `entryCondition`：如何进入场景
- `completionCondition`：如何完成场景
- `exitCondition`：如何离开场景
- `unresolvedDependencies`：尚未实现但不能影响本场景的依赖

## 7. 第一版《高墙之外》切片建议

### 7.1 范围选择

建议制作 `S_LIVING`「客厅观影」，而不是把 `S_MENU`「标题」当作正式玩法场景。

- `S_MENU`：启动界面，只负责新开始、继续和重新开始。
- `S_LIVING`：第一个正式叙事场景，承担观影、背景建立和异常白光转场。

### 7.2 建议纳入的事件

- `P01`：标题与开始，作为最小启动入口
- `P02`：客厅观影
- `P03`：前情与被卷入

### 7.3 本轮不制作

- 庭院和大门
- 手术室之后的牢房探索
- 摇杆移动教学
- 收音机小游戏
- 书架整理和圣经获取
- 藏锤、挖掘、账本和逃离
- 瑞德寻树、驾驶和海滩结局
- 其他场景、小游戏和完整主线验收

### 7.4 第一版完成判定

玩家应能：

1. 从标题页点击开始。
2. 进入客厅。
3. 推进观影段落。
4. 看到电视异常和白光转场。
5. 读取符合当前认知范围的前情信息。
6. 暂停、继续和重新开始。
7. 在场景切片结束处正常退出或返回标题。

本轮不应进入庭院，也不应伪装成完整游戏已经完成。

## 8. 对 Agent 的上下文加载策略

Agent 不应在每次任务中默认读取整个 YAML。建议按以下顺序加载：

1. 读取项目固定规则文件的相关章节。
2. 读取场景切片的元数据和当前场景。
3. 读取当前事件及其直接依赖。
4. 读取必要角色、物件、状态、信息和玩法。
5. 只有遇到未解析引用时，才回查完整 YAML 的对应 ID。

完整 YAML 保留在工作区，但通过文件定位和 ID 查询按需读取，不作为默认全文提示词。

## 9. 费用与时间预期

场景切片不保证每次都能线性减少所有费用，因为最终仍可能需要：

- 读取规范
- 读取场景切片
- 设计和实现代码
- 生成素材
- 构建和真实浏览器测试
- 失败后的定向修复

但它通常可以减少：

- 初始上下文大小
- 无关内容理解时间
- 远期事件造成的设计分支
- 因长上下文导致的重复重试
- 当前场景之外的素材和机制规划

预计最大的收益不是简单地“少传文本”，而是减少错误范围和返工次数。

## 10. 一致性和回写机制

场景切片不能成为新的事实源。建议每个切片保存：

- 完整 YAML 的版本哈希
- 生成时间
- 场景 ID
- 切片包含的 ID 列表
- 切片引用的外部 ID 列表

当完整 YAML 发生以下变化时，应重新生成受影响切片：

- 当前场景布局变化
- 事件前置条件变化
- 角色在场或知识边界变化
- 物件用途或归属变化
- 状态初值或变化规则变化
- 全局规则变化
- 场景出口或主线顺序变化

如果只是对白措辞变化，可以只重新生成相关事件和审查结果；如果是状态、玩法或场景关系变化，则需要重新构建和测试受影响链。

## 11. 失败处理

如果场景切片缺少关键依赖，Agent 不应自行忽略或凭空补写原作事实。应区分：

- 普通画面、布局、颜色、提示措辞：可以由 Agent 设计并记录。
- 关键人物动机、因果关系、物件用途、条件和结局：必须回查完整 YAML 或记录阻塞。
- 当前场景不需要的远期内容：可以只保留引用，不展开。

如果切片边界导致无法判断，应优先补充切片索引，而不是把整份 YAML 永久重新塞入每一轮上下文。

## 12. 对当前项目实现的建议

项目可以继续保留完整 YAML 上传和原样保存，同时增加以下组件：

1. YAML 解析和唯一 ID 索引器。
2. 引用关系图和反向依赖查询。
3. `scene-slice` 提取器。
4. 切片版本哈希和来源记录。
5. 按需回查完整 YAML 的 ID 查询接口。
6. 场景范围下的构建和验收规则。
7. 场景切片结果与完整 YAML 的一致性检查。

当前工作台已经有项目范围字段和 YAML 原样保存的基础，但还需要进一步把“完整 YAML 读取”落实为真正的场景切片提取，而不是只在提示中要求 Agent 自己缩小范围。

## 13. 希望 DeepSeek 重点评审的问题

请重点评估以下问题：

1. 将完整 YAML 作为权威数据库、场景切片作为 Agent 工作输入，是否是合理的职责分离？
2. 场景切片的最小闭包应包含哪些实体，哪些内容可以只保留 ID 引用？
3. 应该按场景切片，还是按事件、玩法和依赖图切片？
4. 对中文 YAML，使用字符数、字节数还是 tokenizer token 数作为上下文预算更合适？
5. 场景切片遗漏依赖时，如何用低成本方式自动发现并回查？
6. 完整 YAML 修改后，如何计算受影响场景并避免不必要的重生成？
7. 如何防止 Agent 把切片中缺失的内容误认为“没有发生”？
8. 第一版是否应先做静态切片和校验，再加入自动按需回查？
9. 对单场景原型，规范 Markdown 应该完整读取，还是也应拆成相关章节？
10. 这种方案在生成时间、费用、准确性和返工率之间的主要风险是什么？

## 14. 暂定结论

完整 YAML 不应被删除，也不应继续作为每次局部生成的完整输入。

暂定采用：

```text
完整 YAML = 权威事实源
Markdown 规范 = 内容和验收规则
场景索引 = 依赖定位层
场景切片 = 当前 Agent 工作输入
运行验收 = 实现是否真正完成的依据
```

第一版先用 `S_LIVING` 验证这条链路，再根据生成质量、耗时、上下文大小和遗漏依赖情况调整切片算法。
