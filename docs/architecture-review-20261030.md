## 一句话结论

这套架构有意把流程编排交给 Codex，把验收交给宿主。这样可以支持不同故事采用不同玩法，也避免模型自报完成；代价是提示词、技能库、运行时合同和证据链承担了大量流程复杂度。当前最值得修正的不是整个架构，而是把关键规格集中起来，并把高频调试路径从正式全量验收中拆出来。

## 已核对的项目事实

- `executeAutonomous` 使用有界的 12 回合循环，并在工具调用后检查取消、重复失败、候选指纹和正式验收状态。
- `cw_build_test` 当前会完成配置检查、编译、真实浏览器旅程、证据收集和结果写入；`graybox` 与 `formal` 已区分。
- `cw_assets` 可以嵌套调用 Codex，单次调用的超时可达 30 分钟；主 Codex 的思考计时会跳过宿主工具执行时间。因此 12 回合不是完整 run 的 wall-clock 上限。
- `cw_review` 使用单独的审阅 prompt、只读路径保护和截图证据，但仍使用同一模型体系，不能等同于换模型或人工审阅。
- 队列 `service.queue` 在内存中；项目、run、task 和事件记录保存在 SQLite。重启时，`recover()` 会把运行中的任务标记为失败并提示继续；排队数组本身不会自动重建。
- v2 版本优先使用 `acceptance.{fingerprint,buildHash,evidenceHash}`；旧版本仍可通过 `trustSignature` 读取，属于兼容分支。
- `packages/runtime`、`pixel-story-kit`、`interstellar-dust` 和预构建的 `public/local-games/dust` 存在代码或产物分叉，但它们承担的角色不同，不能简单视为四份等价的生产引擎。
- 在当前 Windows 环境执行 `npm test` 得到 99 项通过、17 项失败。失败主要涉及测试夹具路径拼接、符号链接权限和虚构 Codex 可执行文件，不应直接等同于生产功能失败；跨平台验证需要单独修复和记录。

## 问题与判断

### 1. 关键规格没有单一来源（P0）

“约 10 分钟、至少 5 个有效场景、简单小游戏”等要求同时出现在 `productionPrompt`、`checkProject`、`PRODUCTION-CONTRACT.md`、技能参考文件和工作区说明中。当前这些内容保持一致，但没有机制防止以后只修改其中一处。

风险是门槛漂移：模型按照旧提示词制作，正式校验却按新阈值拒绝，错误看起来像模型能力问题。

建议建立结构化规格合同，例如 `spec.json` 或 TypeScript schema，由提示词、正式校验、UI 文案和文档生成。时间目标应标注为内容估计，不能被误解为自动测试时长。

### 2. 正式构建工具承担了过多反馈职责（P0/P1）

`cw_build_test` 的完整职责适合交付前验收，但不适合每次碰撞或配置修改都执行。建议增加：

| 工具 | 作用 |
| --- | --- |
| `cw_compile` | 配置、引用、插件、可达性和构建清单 |
| `cw_replay({journeyId})` | 只重放一条已声明旅程，保留真实输入和证据格式 |
| `cw_build_test` | 正式全量路线、正式证据和最终构建 |

这不是删除正式检查，而是缩短高频修复反馈环。

### 3. 回合上限不能代表成本或等待上限（P1）

宿主工具执行期间，Codex 主调用的思考计时暂停；素材生产还可能启动嵌套 Codex。当前设计有清晰的取消和部分成果保留机制，但用户无法从“12 回合”推断总等待时间。

建议为整个 run、单个资源批次和单个宿主工具增加 wall-clock 预算，并在 UI 中显示“模型回合预算”和“工具执行时间”两个独立指标。素材生产是否改成异步作业，可在时间预算仍不足时再实施。

### 4. “独立审阅”应降低承诺强度（P2）

当前审阅能够防止模型只凭自述宣布完成，也有只读保护和证据绑定，这是有效的二次检查；但它仍是同一模型体系内的语义审阅，无法排除系统性审美或判断盲区。

建议将产品和文档中的名称改为“二次语义审阅”或“模型二次审阅”，并明确人工、异模型或真人体验仍是更高等级的证据。

### 5. 运行时源码和构建产物存在分叉（P1）

维护风险是真实的：修复运行时问题时，开发源码、故事样本、kit 和预构建产物可能不同步。原审阅把它概括为“四份引擎”，但这些目录并非完全等价：`packages/runtime` 是工作台运行时，`pixel-story-kit` 是可复用 kit，`interstellar-dust` 是故事样本，`public/local-games/dust` 是发布内容。

建议明确一份 canonical runtime；其余目录在仓库约定中标记为 fixture、示例或构建输出，并由脚本从 canonical runtime 生成或校验，而不是依赖人工 SHA 对照。

### 6. 队列重启后不会自动重放（P1/P2）

“任务凭空蒸发”并不准确：run 和事件仍在 SQLite 中，重启会留下失败状态并允许用户继续。真正的问题是排队顺序和等待状态没有持久化，服务重启后不会自动恢复排队任务。

如果目标是本地单进程工作台，现有“失败后继续”机制可以接受；如果要支持后台运行、无人值守或多任务排队，应把 queue entry、顺序、尝试次数和取消状态写入 SQLite，并在启动时重建内存队列。

### 7. 旧 HMAC 与 v2 acceptance 并存（P2）

这是兼容债务，不是当前 v2 验收绕过。`verifyTrusted` 对新版本使用指纹、构建哈希和证据树，对旧版本保留 HMAC 读取路径，符合项目文档中的迁移策略。

建议记录旧格式的最后写入版本和停止日期；新代码停止产生 HMAC，达到过期时间后再拒绝旧版本，避免永久保留两套推理规则。

### 8. 技能库规模大于宿主代码，语义回归仍不足（P1/P2）

技能库约 3 万行，现有检查主要覆盖入口、清单、版本和结构，不能证明所有提示词和参考资料在长期修改后仍然有效。解决方案不是给提示词强行编写大量单元测试，而是为每个关键技能保留少量契约样例，并对代表性故事运行完整生成、真实输入和验收回归。

## 应保留的设计

1. `cw_finish` 后锁定候选，并再次核对指纹、构建哈希和证据树，能防止“宣布完成后继续改文件”。
2. `evidenceKind: 'host' | 'model'` 把模型自述和宿主观测分开，数据结构和 UI 都遵守这一边界。
3. 取消、连续无进展、同错三次熔断和 12 回合边界，避免无限循环。
4. 正式覆盖率使用真实观察到的场景和机制操作，而不是只数声明配置。
5. 候选版本、正式版本、回退和存档版本彼此隔离，适合继续制作和失败恢复。

## 建议实施顺序

| 优先级 | 事项 | 目标 |
| --- | --- | --- |
| P0 | 单一规格合同 | 消除提示词、校验器和文档的阈值漂移 |
| P0/P1 | `compile` 与单旅程 replay | 缩短碰撞、配置和机制修复反馈环 |
| P1 | canonical runtime 与 fixture 边界 | 降低运行时分叉和发布产物漂移 |
| P1 | wall-clock 与工具预算 | 让嵌套素材任务的等待和成本可预期 |
| P1/P2 | SQLite 持久化队列 | 支持重启后的队列重建和无人值守运行 |
| P2 | 审阅命名与证据等级对齐 | 避免把模型二次审阅误解为人工独立审查 |
| P2 | HMAC 迁移和过期计划 | 逐步移除兼容分支 |
| P2 | 技能契约样例与跨平台测试 | 提高技能语义和 Windows 验证的可信度 |

最终建议是增量修正，不推倒重来。项目当前的证据边界、候选隔离和宿主验收值得保留；先集中规格、拆分反馈路径，再处理运行时归属、队列和兼容债务，收益最高。

## 验证记录说明

规模统计和 SHA-256 比对适合发现重复与分叉，不足以证明功能等价。自动浏览器速通也不能证明真人约 10 分钟体验。任何后续审阅都应分别记录程序检查、宿主真实输入、视觉读图、模型语义判断和真人体验，不能用其中一类证据替代另一类。
